# Part 1: 用户场景清单

> 本部分使用业务语言描述，可直接分享给产品经理和业务方确认。

## 领域: 用户登录与身份

### S-001: 首次登录

- **角色**: 普通用户
- **触发**: 管理员在后台创建了账号，用户第一次打开 Polo AI 桌面端
- **期望**: 直接看到登录页面（用户名 + 密码），输入后进入主界面
- **异常**:
  - 密码错误 → 提示"用户名或密码错误"，不透露具体是哪个错
  - 账号被禁用 → 提示"账号已被禁用，请联系管理员"
  - 网络不通 → 提示网络错误
- **优先级**: P0

### S-002: 日常打开（近期活跃用户）

- **角色**: 普通用户
- **触发**: 用户最近一周内用过，再次打开 app
- **期望**: 直接进入主界面，不需要输密码，无任何等待
- **优先级**: P0

### S-003: 长时间未使用后打开

- **角色**: 普通用户
- **触发**: 用户超过一周没打开 app
- **期望**: 需要重新输入用户名和密码
- **优先级**: P1

### S-004: 主动登出

- **角色**: 普通用户
- **触发**: 用户想换账号或换电脑前主动登出
- **期望**: 在左下角点击用户头像/名字，弹出菜单中有"登出"选项，点击后回到登录页
- **优先级**: P0

### S-005: 忘记密码

- **角色**: 普通用户
- **触发**: 用户忘记了登录密码
- **期望**: 联系管理员，管理员在后台重置密码，用户用新密码登录
- **异常**:
  - 登录页不需要"忘记密码"链接（没有自助找回流程）
- **优先级**: P1
- **备注**: 不做自助找回，管理员手动重置

### S-006: 账号被禁用（离线状态）

- **角色**: 已离职用户
- **触发**: 管理员在后台禁用了用户账号，用户下次打开 app
- **期望**: 跳到登录页，显示"账号已被禁用，请联系管理员"
- **优先级**: P1

### S-007: 账号被禁用（在线状态）

- **角色**: 正在使用的用户
- **触发**: 用户正在用 app 聊天，管理员此时禁用了该账号
- **期望**: 当前正在进行的会话不中断，可以继续完成。下一次发消息或下一次打开 app 时生效
- **优先级**: P2
- **备注**: 不需要立即踢下线，延迟生效可接受

## 领域: AI 服务配置下发

### S-008: 登录后获取 AI 服务

- **角色**: 普通用户
- **触发**: 用户登录成功
- **期望**: 自动获取管理员为该用户配置的 AI 服务列表，用户可以直接开始使用
- **优先级**: P0

### S-009: 用户切换默认 AI 服务

- **角色**: 普通用户
- **触发**: 用户想换一个常用的 AI 模型
- **期望**: 可以在管理员配好的多个 AI 服务中选择一个作为默认，但不能添加/删除/修改服务本身
- **优先级**: P1

### S-010: 管理员更新配置实时生效

- **角色**: 管理员（在后台操作） + 普通用户（在桌面端）
- **触发**: 管理员在后台修改了用户的 AI 服务配置（比如新增了一个模型、删除了旧模型）
- **期望**: 用户那边 1 分钟内看到变化，不需要重启 app
- **优先级**: P1

### S-011: 不同用户不同配置

- **角色**: 管理员
- **触发**: 管理员给不同用户配置不同的 AI 服务组合
- **期望**: 小明看到基础版 AI 服务，小红看到高级版 AI 服务，互不影响
- **优先级**: P1

### S-012: 多设备登录

- **角色**: 普通用户
- **触发**: 小明在公司电脑已登录，回家在笔记本也想登录同一账号
- **期望**: 笔记本登录成功后，公司电脑自动被踢下线（下次操作时跳回登录页）。同一账号只能在一台设备上使用
- **优先级**: P1

### S-013: 未配置 AI 服务

- **角色**: 普通用户
- **触发**: 管理员创建了账号但还没配置 AI 服务，用户登录后
- **期望**: 可以进入主界面，但发消息时提示"管理员尚未为你配置 AI 服务"
- **优先级**: P1

## 领域: 用量与额度

> **背景**: AI 服务由第三方 Provider 提供，第三方自身有 token 额度限制和硬截断能力。我们的额度系统主要用于**内部统计和与第三方对账**，不需要做精确的硬截断——第三方已经兜底了。

### S-014: 查看用量

- **角色**: 普通用户
- **触发**: 用户想看看自己本月用了多少
- **期望**: 在 app 中能看到本月已用量和总额度
- **优先级**: P1

### S-015: 额度快用完时提醒

- **角色**: 普通用户
- **触发**: 用户的本月用量接近额度上限（阈值由管理员设置，默认 80%）
- **期望**: 提前收到提醒（比如"你本月额度已使用 80%"），不是用完了才知道
- **优先级**: P1

### S-016: 额度用完

- **角色**: 普通用户
- **触发**: 用户本月额度已耗尽
- **期望**: 提示"本月额度已用完，下个周期将自动重置"。已经在进行的对话让它自动跑完，不需要复杂的中断逻辑——第三方 Provider 有自己的硬限制兜底
- **优先级**: P1
- **备注**: 我们的额度检查是"软限制"，用于提前预警和对账。第三方 Provider 的硬限制是真正的安全网

### S-017: 额度按月重置

- **角色**: 系统自动
- **触发**: 到达用户的额度重置日（每月固定日期，管理员可按用户设置不同的重置日）
- **期望**: 额度自动恢复，用户可以继续使用
- **优先级**: P0
- **备注**: 重置日期按用户可配，比如小明每月1号重置，小红每月10号重置

# Part 2: 技术推导

> 本部分由 Claude 从用户场景自动推导，供开发团队参考。
> 每个技术决策都关联到 Part 1 中的场景编号，确保可追溯。

## 认证方案

| 技术决策 | 值/方案 | 推导来源 | 推导理由 |
|---------|--------|---------|---------|
| 认证协议 | JWT access token + refresh token | S-001, S-002, S-003 | S-001 需要登录获取凭证；S-002 要求一周内免登录→本地需持久化凭证；S-003 定义了超时边界→需要自动过期机制 |
| Access Token 有效期 | 7 天 | S-002, S-003 | S-002 "一周内用过直接进" → access token 在7天内有效，本地校验即可，无网络开销 |
| Refresh Token 有效期 | 30 天 | S-003 | S-003 "超过一周" 需重登录，但应给一个合理的静默续期窗口。7-30天内打开→静默刷新无感；>30天→必须重新输密码 |
| Token 刷新策略 | Refresh token rotation | S-002, S-012 | 每次用 refresh token 换新的 access+refresh pair，旧的作废。同时实现单设备登录：新设备登录时 revoke 旧 refresh token |
| 单设备限制 | 登录时 revoke 该用户所有已有 refresh tokens | S-012 | 同一账号只能一台设备→新设备登录自动踢旧设备。旧设备的 access token 7天内自然过期，refresh 时被拒绝 |
| 密码验证算法 | Argon2id | S-001 | 需要密码登录，Argon2id 是当前推荐的密码哈希算法 |
| 错误信息策略 | 统一模糊提示 | S-001 异常 | "用户名或密码错误"不透露具体原因，防止枚举攻击 |
| Token 存储 | 加密本地存储 (Credential Manager) | S-002 | 免登录需要本地持久化 token，使用现有的 AES-256-GCM 加密凭证存储系统 |

## 账号状态管理

| 技术决策 | 值/方案 | 推导来源 | 推导理由 |
|---------|--------|---------|---------|
| 禁用生效时机 | 延迟生效（access token 自然过期） | S-006, S-007 | S-007 要求当前会话不中断→不需要实时踢下线机制。access token 7天内过期，refresh 时拒绝即可 |
| 禁用检查点 | refresh token 刷新时 + validate 端点 | S-006 | S-006 要求下次打开时拒绝→在 token 刷新或 validate 时检查账号状态 |
| 密码重置 | Admin 后台操作 + revoke 所有 refresh tokens | S-005 | 无自助找回流程，管理员重置后需使旧 token 失效 |

## 登出与会话

| 技术决策 | 值/方案 | 推导来源 | 推导理由 |
|---------|--------|---------|---------|
| 登出实现 | Revoke refresh token + 清除本地 token | S-004 | 登出后 access token 7天内自然失效，refresh token 立即作废 |
| 登出位置 | 用户头像下拉菜单 | S-004 | 用户期望在左下角头像菜单中找到登出 |

## AI 服务配置同步

| 技术决策 | 值/方案 | 推导来源 | 推导理由 |
|---------|--------|---------|---------|
| 配置获取时机 | 登录成功后 + 定期轮询 / 事件推送 | S-008, S-010 | S-008 登录后立即获取；S-010 要求实时生效→需要变更检测机制 |
| 配置变更检测 | configVersion 比对 + 短轮询（30-60秒间隔） | S-010 | "1分钟内生效"→轮询间隔30-60秒即可满足，无需 WebSocket |
| 用户可操作范围 | 只能切换默认 AI 服务，不能增删改 | S-009, S-008 | S-009 允许切换默认；但服务列表完全由管理员控制 |
| 连接标记 | `managedBy: 'admin'` 字段 | S-009 | 区分管理员下发的连接和（未来可能的）用户自建连接，前者不可编辑/删除 |
| 按用户差异化 | Admin API 按 user ID 返回不同连接列表 | S-011 | 不同用户不同配置→API 返回当前用户关联的连接 |
| 未配置处理 | 允许进入主界面，发消息时校验并提示 | S-013 | 不阻止登录，在实际使用时才提示无可用 AI 服务 |

## 配额系统

> **设计原则**: 我们的配额是"软限制"（预警 + 对账），第三方 Provider 的额度是"硬限制"（真正断开）。因此不需要复杂的实时精确截断逻辑。

| 技术决策 | 值/方案 | 推导来源 | 推导理由 |
|---------|--------|---------|---------|
| 配额定位 | 软限制：预警 + 对账，非硬截断 | S-016 | 第三方 Provider 已有硬限制兜底，我们只需统计和提前预警 |
| 配额周期 | 按月，重置日管理员按用户可配 | S-017 | 不同用户可有不同重置日期（如1号、10号） |
| 配额检查时机 | 发消息前软检查 | S-016 | 额度已尽时提示用户，但不需要做精确的 token 级截断 |
| 超额处理 | 提示信息，让进行中的对话自然结束 | S-016 | 不做复杂中断逻辑。第三方会在真正超额时硬截断 |
| 预警阈值 | 管理员可配（默认 80%） | S-015 | "快用完时提前提醒"→阈值管理员可按用户或全局设置 |
| 用量展示 | app 内可查看已用/总额 | S-014 | 用户需要知道自己的用量状态 |
| 用量上报 | 每次 AI 对话完成后异步上报 | S-014, S-016 | 统计用于对账和展示，对话完成后上报即可，不需要实时精确 |

## 未覆盖的技术决策

> 以下技术决策未在场景中显式确认，采用默认推荐方案。

| 技术决策 | 推荐方案 | 理由 |
|---------|---------|------|
| JWT 签名算法 | HS256 | Admin 和 Polo AI 共享密钥，对称签名足够，性能好 |
| JWT payload 标准 claims | iss=polo-admin, aud=polo-client | 行业标准，防止 token 跨系统误用 |
| Admin URL 配置方式 | 服务端 `ADMIN_API_URL` 环境变量 | 统一 Admin 管理模式，用户无感 |
| API Key 传输安全 | HTTPS 明文传输（不做应用层加密） | HTTPS 已加密传输层，应用层再加密增加复杂度但安全收益不明确 |
| Refresh token 存储 | Admin 数据库 refresh_tokens 表 | 需要服务端校验和 revoke 能力 |
| 配额单位 | Token 数量 | AI 服务计费的行业标准计量单位 |
