0结论速览（TL;DR）

一句话结论：两者不是同一层的东西。OpenUI 是"渲染层接管"的通用 Generative UI 框架（模型输出紧凑 DSL，前端渐进渲染）；我们是"agent 工具调用 + 安全围栏"的产品内实现（模型输出受控 JSON / 沙箱 HTML，交互回流会话）。安全纵深、审计发布链、数据文件化、会话整合我们明显更强；流式渐进渲染、组件丰富度、客户端响应式运行时、token 工程是对方明显更强、且是我们下一步最值得借鉴的四个点。
  • 流式是我们最大的体验差距。OpenUI token 到即渲染（首屏 4.9s vs JSON 方案 14.2s 的口径）；我们的卡片在工具调用 completed 之后才出现（TurnCard.tsx:2911 只取完成态 activity），大表格 / 多组件回合用户等得更久。
  • token 成本上双方走的是两条不同的路，且互补。OpenUI 用紧凑 DSL 省输出 token（-52.8%）；我们用"4KB payload 上限 + 数据必须走 transform_data 文件"从结构上让大额数据根本不经过模型输出。但我们的隐性大头在输入侧：render_ui 的 JSON Schema 工具定义估算 15–25KB（约 4–6K token），比 OpenUI 全组件库的 system prompt（5,031 token / 40+ 组件）还贵——这是最安全、性价比最高的优化点。
  • 对方的"generate vs execute 分离"运行时值得吸收：过滤 / 刷新 / 下钻这类纯视图操作在前端完成、不回模型。我们的交互目前全部坍缩为"塞回聊天输入框"，纯查看操作也要付一次模型往返的延迟和成本。
  • 画布应用全量重写（512KB）是成本黑点。对方增量编辑一屏 UI 只需改 2–3 行（约 60 token）；我们的 updateOf 每次全量重发。
  • 外部文章两处事实需要勘误："需要 Node.js 24" 不实（仓库 engines 为 node ^20.19 || >=22.12）；"OpenRouter" 只是官方 demo 的便利项，框架本身不依赖。"-52.8% token" 是同 AST 格式投影基准，真实生成对比里结构有效率只差 0.8 个百分点（96.5% vs 95.7%），差距主要在成本与失败形态。

1方案速览

OpenUI（thesysdev/openui）开源框架

  • 定位："The Open Standard for Generative UI"，框架无关的全栈 GenUI 方案；MIT；11,645 stars / 794 forks。
  • 原理：模型不写网页代码，输出自研 DSL OpenUI Lang（行导向赋值语句、位置参数、命名引用），前端从注册组件库里渐进渲染。
  • 流式：每 chunk 全量重解析 + autoClose() 括号补齐容错 + 行级静默跳过；部分渲染代替白屏。
  • 组件：内置 40+ 组件（Table / Charts(Recharts) / Form / Calendar / Carousel / Tabs / Map 类…），两个预置库（通用 + 聊天优化）。
  • 运行时：Query/Mutation + $var 响应式，交互（过滤 / 提交 / 刷新）不经模型；工具默认在浏览器执行。
  • 生态：React / Vue / Svelte / Angular 渲染器 + email + A2UI 桥 + LangChain/Vercel AI SDK 集成（Lang 1.0 特性目前 React-only）。
  • 维护：Thesys Inc 单公司主导，Changesets 高频发布（Lang 1.0 于 2026-10-12），配套商业托管（Gateway / Autofix / 观测云）。

Polo genui/impl产品内实现

  • 定位：Electron 桌面 agent 的两条 GenUI 轨道：内联卡片（render_ui）+ 画布应用（generate_app）；相对 baseline +11,878 行 / 90 文件，17 个提交（POO-101~104 + formatting / row-actions / confirm-flow）。
  • 原理：模型调用 session 工具输出受控 JSON（6 组件判别联合，payload ≤4KB）或单文件 HTML（≤512KB，updateOf 全量重写）。
  • 渲染：完成后一次性渲染；同 id 复用 = 卡片原地更新；未知 type 回退只读 JSON 视图（信息永不丢失）。
  • 数据：表格行数据 schema 层硬拒绝 inline，必须先 transform_data 落会话 data/ 再用 src 引用——大额数据不经过模型输出。
  • 交互：全部坍缩为"塞回聊天输入框"（send-message / fill-input）+ 画布 ui-event 深链（六步校验、10 ev/s 限速、capability 声明）。
  • 安全：三层纵深（生成侧实体解码静态扫描 → 运行时请求围栏 file:/data:/blob: + deny-all 权限 → ui-event 所有权绑定）；审计先行的 pin / publish 链。
  • 治理：组织级远端 rollout × 用户级 kill switch 两级闸门；schema 版本化快照 + 发布链确定性 zip。

同一个"销售表"在两种方案下的样子

OpenUI Lang 模型直接输出（433 字节，来自仓库 benchmarks/samples/simple-table.oui）：

root = Stack([title, tbl])
title = TextContent("Employees (Sample)", "large-heavy")
tbl = Table(cols, rows)
cols = [Col("Name", "string"), Col("Department", "string"),
        Col("Salary", "number"), Col("YoY change (%)", "number")]
rows = [["Ava Patel", "Engineering", 132000, 6.5], ...]

Polo render_ui 模型输出工具调用 JSON（数据另行落文件，来自 render-ui.test.ts）：

{ "components": [{
  "id": "sales", "type": "data-table",
  "title": "Sales by Region",
  "columns": [
    {"key":"region","label":"Region","type":"text"},
    {"key":"revenue","label":"Revenue","type":"currency"}],
  "src": "/abs/.../data/sales_by_region.json",
  "pageSize": 20 }] }
注意对照点：OpenUI 的行数据仍在模型输出流里（基准均值 1,362 token/屏）；我们的行数据在文件里，payload 恒 ≤4KB——数据密集场景我们更省，布局密集场景对方更省。同时对方靠命名语句 + 位置参数消灭了 "component"/"props"/"children" 重复键，这正是它 -52.8% 的机制来源，也是我们 JSON 里付的"格式税"。

3关键差异深读

3.1 token 哲学：紧凑 DSL vs 数据文件化（互补，不是对立）

OpenUI 的 -52.8% 来自四个结构性手段：位置参数消灭重复键、命名语句 + 引用让子组件平铺不嵌套、键名无引号、top-down 生成（骨架行先出）。它优化的是"布局与控件的描述成本"。

我们的路线是让大额数据根本不走模型输出：payload 4KB 硬上限 + data-table 的 src 强制文件化 + 画布数据 payloadSrc ≤1MB。一张 2 万行的表，对方要模型逐行吐出来，我们只是 transform_data 产物。在"数据密集"场景我们的输出 token 成本接近常数，对方线性增长。

但我们有一块被忽视的输入侧成本：render_ui 的 inputSchema（zodToJsonSchema 产物）估算 15–25KB ≈ 4–6K token，每个会话每轮都付。OpenUI 用 5,031 token 描述了 40+ 组件，我们用相近的 token 描述 6 个组件。原因是 JSON Schema 工具定义天然冗长（60 个叶子字段的类型 / 描述 / 约束全量序列化），而对方只注入"组件签名行"（如 Form(id: string, buttons: Buttons, controls: FormControl[]) — Form container）。这里不需要换输出格式就能吃到大部分收益——见借鉴清单 P1-1。

3.2 流式：渐进渲染 vs 完成后渲染

OpenUI 的流式实现工程上其实"简单粗暴"：每个 chunk 到达就全量重解析整个前缀，靠解析快换简单性；截断输入用 autoClose() 补引号补括号，无效行静默跳过；错误扣到流结束才上报。生产管线还叠了一层"解析错误 → 小 sanitizer 模型只修坏行"的自修复（宣称 <1% 屏幕损坏触达用户）。

我们的"完成后渲染"换来的是用户永远看不到无效 UI：Zod 全量校验失败 → 工具错误带 issue 列表 → 模型修复重试一次 → 只渲染成功 payload。代价是大 payload 的首卡延迟（模型边生成边算，用户在等）。

两者可以折中：骨架预览（partial JSON 容错解析出组件类型和标题先占位）+ 完成后校验替换正式内容，既保住"永不显示坏 UI"的底线，又拿到首屏提前量。Claude API 本身流式提供 tool input delta，管线原料是现成的。

3.3 交互模型：generate vs execute 分离 vs 聊天回路

这是两个方案最深的架构分歧。OpenUI 的口号是"generate vs execute 分离"：模型只生成一次接线（Query / Mutation / $var），之后过滤、排序、刷新、提交全部在前端运行时执行，不惊动模型。

我们把一切交互坍缩为"下一条用户消息"：按钮 = send-message/fill-input，表单提交 = values JSON 作为用户消息，行操作 = 模板插值后发送。好处是每个语义动作都落在对话记录里，可审计、可追溯、用户全程知情；代价是纯视图操作（换个筛选、钻个维度）也要付一轮模型往返的延迟与费用。

边界其实很清晰："视图态"操作（筛选 / 排序 / 图表联动 / 刷新已落盘的数据）应该留在客户端；"语义"动作（触发分析、执行任务、改变世界状态）走聊天回路。我们的 data-table 已经在客户端做排序过滤了——这条路已经开了个头，只是没有形成体系。

3.4 逃生舱策略：无逃生舱 vs 大逃生舱

OpenUI 没有逃生舱：模型只能用注册组件，表达力上限就是组件库。要新表达力，得开发注册新组件。

我们有一个大逃生舱：generate_app 直接产完整 HTML（跑在三层围栏的 webview 里）。这解释了为什么我们的内联组件可以只有 6 个——复杂 UI 走画布。代价是：画布应用每次迭代 512KB 全量重写、模型要写整页 HTML（生成慢、易错）、且画布内容无法被宿主结构化理解（对模型回流的只有 ≤2KB 的 modelContext）。

对方路径的问题反过来：没有逃生舱，地图、复杂可视化都依赖组件库持续扩张（他们内置 40+ 还在长）。我们的双层结构（6 内联组件 + 画布）本质上是"80% 场景用高结构化低保真，20% 场景用低结构化高保真"——这个分层本身是对的，问题只在中间层太薄：chart、简单布局组合这类"中等复杂度"需求目前要么降级成表格、要么升级成整页 HTML。

4优劣势对比

4.1 我们相对 OpenUI 的优势（保持并对外讲清楚）

  1. 安全纵深是代差级的。对方的安全模型是"schema 白名单 + 非可执行 DSL"，工具默认跑在浏览器里、无 per-tool 权限；我们是生成侧扫描（实体解码 + data: URI 递归解包）→ 运行时请求围栏（仅 file:/data:/blob:）+ deny-all 权限 + 无弹窗无导航 → ui-event 六步校验（sender↔card 所有权绑定、attach 时文档 capability 提取为信任根、10 ev/s 限速）。桌面 + 企业场景这是硬需求，对方方案不能直接替代。
  2. 数据文件化让输出 token 成本近常数。对方均值 1,362 token/屏全部从模型输出流里过；我们的表格行进 transform_data 文件，payload 恒 ≤4KB。数据密集场景成本与延迟双双占优。
  3. 交互全程可审计。语义动作必然进对话记录；画布事件带 modelContext 注入防线（剥 system-reminder 字样、码点安全截断、注入式攻击有专门测试）。
  4. 版本化回放 + 确定性发布链。schema 快照按生成时版本回放（未知版本 fail-closed）；pin/publish 审计先行、确定性 zip 字节可复现、远端 policy 只能收紧。对方没有对应物。
  5. 产品级 rollout 治理。组织开关 × 用户 kill switch 两级相交、资格矩阵每回合重算、Pi 子进程三层 deny——渐进发布需要的旋钮齐全。
  6. 与既有会话 / tab / admin 体系深度整合（pin 进启动器、publish 走既有 Creator App 链），这是框架型方案给不了的。

4.2 我们相对 OpenUI 的劣势（对方强项 = 我们的差距）

  1. 无流式渐进渲染——首卡延迟差距的最大来源；对方骨架先出、数据后至，我们整块等校验。
  2. 组件表达力薄。6 vs 40+；无 chart（Mermaid xychart 只是过渡）、无布局组合（Stack/Tabs/Card 层级）、无日历 / 轮播等。中间层缺位，需求被两头挤压。
  3. 纯视图交互也要付模型往返。对方 $var 响应式 + Query 重取在前端闭环；我们换个筛选也是一轮会话。
  4. 画布应用全量重写。512KB updateOf vs 对方改 2–3 行（~60 token）的增量编辑；长迭代会话里成本与延迟都被放大。
  5. 输入侧 token 效率低。工具 schema 估算 4–6K token vs 对方 5K token 描述 40+ 组件（签名式 prompt）。
  6. 画布无运行时数据绑定。对方 Query/refreshSec 让应用活起来；我们的画布是静态快照，要更新只能靠模型重写。

4.3 OpenUI 自身的坑（我们不必羡慕的部分）

  • 过宽容错是把双刃剑：无效行静默跳过（#582 用户抱怨想更严格）、stripFences 行中 fence 整段空白（#1440）、流式图表 null 崩溃（#355）、assistant-ui 更新深度爆栈（#990）——流式健壮性是他们自己也还在修的领域。
  • 框架运行时不對等：Lang 1.0 特性（自定义函数 / 动作 / 存储协议）React-only，Vue/Svelte/Angular 停在 0.5。
  • 工具浏览器执行 + 无权限模型：docs 明言 Renderer 是 client component、函数跑在浏览器，鉴权靠应用自觉——在他们的 Web 场景成立，在我们的桌面 agent 场景不成立。
  • 单公司主导 + 商业化分流：核心开源但 Gateway/Autofix 是托管服务；重名争议（与 W3C OpenUI）未解。
  • DSL 的隐藏成本：自定义格式 = 自建解析器 + prompt 工程 + 模型适配全要自己扛；他们真实生成对比里结构有效率 96.5%（即每屏 ~3.5% 概率结构性失败要靠容错兜）——JSON 工具调用在模型侧的"原生正确率"更高，这是我们的结构性红利。

5可借鉴清单（按优先级）

以下每项都标注了落地缝隙（seam）——即 genui/impl 里已经存在的、专门为这类扩展预留的接口。优先级按「体验收益 × 实现风险」排定，P0 = 建议下一迭代立项，P1 = 排期，P2 = 观察项。

P0-1 · 纯视图交互的客户端闭环（generate vs execute 分离）

收益：高（交互延迟从一轮会话 → 毫秒级，省模型费用） · 风险：低 · 缝隙：MarkdownDatatableBlock 已有客户端排序 / 过滤 + renderColumnCell/renderRowAction 钩子；action 语义已二分（send-message / fill-input）

借鉴点：OpenUI 的 $var 响应式让"视图态"操作零模型往返。把这条边界制度化：视图态操作（筛选、图表联动、列选择、刷新已落盘数据、下钻导航）在前端完成；语义动作（触发分析 / 执行任务）保持走聊天回路。

具体起步：data-table 增加"客户端下钻视图"（点击行 → 本地按维度重聚合，数据文件已全量在客户端，transform_data 产物就是全量数据）+ 图表组件（见 P1-3）的图例 / 区间筛选。send-message 只留给真正需要模型的位置。

P0-2 · render_ui 骨架流式预览

收益：高（首卡出现时间大幅提前） · 风险：中（需容错解析，但显示层可保守） · 缝隙：Claude API 已流式提供 tool input delta；TurnCard 的 activity 解析点（TurnCard.tsx:2911）是唯一消费口

借鉴点：OpenUI 的 autoClose + 部分渲染。我们不需要学它的"边流边渲染真组件"，学它的分层：partial JSON 容错解析出「组件类型 + 标题」先出骨架占位卡，completed 后过 Zod 校验再替换正式内容。

边界保住我们的原则：骨架不渲染业务数据（防显示后回缩），只显示"正在构建 data-table「Sales by Region」…"级别的结构预告——用户感知从"黑箱等待"变成"看得见的装配"。

P1-1 · 工具 schema 瘦身（签名式 prompt，最大性价比）

收益：高（每会话每轮省 est. 3–5K token 输入） · 风险：低 · 缝隙：POO-104 的两层索引已确立"目录进描述、schema 永不进 prompt"原则——把它推进到 schema 本身

借鉴点：OpenUI 5,031 token 描述 40+ 组件，靠的是"组件签名行"（Form(id, buttons, controls) — Form container）而非全量 JSON Schema。我们的 zodToJsonSchema 产物估算 15–25KB，其中 describe() 文本约 2KB，其余是结构性冗余。

做法：(a) 收紧 zodToJsonSchema 输出（剔除默认值重复、精简约束序列化）；(b) 把字段级语义说明继续往目录描述层挪（那里已有 160 字符 / 条的 sanitize 信任边界）；(c) 评估 generate_app 的"单字符串参数 + 协议写在描述里"模式是否适用于 render_ui 的低频组件。先实测（当前 4–6K 是估算值），再动手。

P1-2 · chart 组件重启评估（ADR 0021 的条件 a 已满足）

收益：中高（补齐中间层最明显的洞） · 风险：中 · 缝隙：ADR 0021 预设的两条缝——render_ui registry 新卡类型，或 bundle policy 白名单 vendored 单文件

事实：ADR 0021 的重启条件是 "(a) P2 交互循环落地且卡片 schema 稳定"。POO-103 ui-event 交互循环已落地、schemaVersion=1 已冻结——条件 a 成立，该 ADR 可以正式重开。OpenUI 的经验佐证需求真实性：Charts 是其高频组件（benchmark 七场景有 chart-with-data，流式崩溃 issue #355 也恰恰出在图表——说明用得多）。

落地路径 honor 既有约束：选无外链 / 无运行时加载的方案（ADR 已点名"vendored 单文件片段"），走 registry 新卡类型缝；数据同样文件化（src 模式），schema 加入 GENUI_COMPONENT_SCHEMAS 与快照注册表。

P1-3 · 画布应用增量编辑（替代 512KB 全量重写）

收益：中高（长迭代会话的延迟 / 成本 / 版本噪声三降） · 风险：中 · 缝隙：ui-event payloadSrc 已支持 ≤1MB 会话 data/ 内 JSON 回读；genui-apps 目录已有 version.json 簿记

借鉴点：OpenUI top-down 生成 + 改 2–3 行 patch（~60 token）的增量编辑。我们不需要给 HTML 打 patch——把"数据"和"结构"分离：引导模型把可变状态放 app.js 里从 data/ JSON 读取（generate_app 描述里已有 payloadSrc 通道），迭代时只 transform_data 更新数据文件，应用经 Query 式轮询（见 P2-1）自刷新；结构变化才走 updateOf。

P2-1 · 画布运行时数据绑定（Query / 轮询）

收益：中（画布应用"活"起来） · 风险：中 · 缝隙：ui-event 深链协议 + payloadSrc 通道现成

给画布应用一个声明式的数据刷新能力：bundle 声明依赖的 data/ 文件列表，宿主在文件变化时经既有 ui_state 协议事件推送新内容（点对点、永不广播的机制已在）。等价于 OpenUI 的 Query(refreshSec)，但数据源限定在会话 data/ 围栏内——比对方的浏览器 fetch 收敛得多。

P2-2 · 自有 token / 延迟 / 有效率基准

收益：中（决策不再拍脑袋） · 风险：无 · 缝隙：无依赖，纯新增

照抄 OpenUI 的两层方法论：(a) 格式投影基准（同一 UI 的 payload / schema token 计数）；(b) 真实生成基准（N 条贴近用户措辞的 prompt × 模型 × 重复次数，量结构有效率 / 均值 token / 首卡延迟）。P1-1 和任何"要不要 DSL 化"的决策都应先有这套尺子。他们的结论也提醒尺度：格式省 52.8% 不等于可靠性差 52.8%——两轴要分开量。

P2-3 · 结构化错误码 taxonomy 辅助重试

收益：低中（重试成功率与轮次） · 风险：无 · 缝隙：render-ui.ts 已把 Zod issues 格式化回给模型（"fix and retry once"）

OpenUI 的错误码体系（unknown-component / missing-required / type-mismatch / excess-args…）设计为可直接回传 LLM 修正。把我们的 Zod issue → 稳定错误码 → 针对性修复提示做一层映射，提升一次重试成功率。

6不建议照搬的部分

  • 全面 DSL 化 render_ui 输出。收益已被我们 4KB 上限 + 数据文件化封顶（输出侧最多省 ~2K token/回合）；代价是自建解析器、双后端（Claude SDK 原生 JSON 工具 / Pi JSON Schema 代理）都要改、模型侧结构正确率从"JSON 原生红利"跌到 ~96.5%。先把 P1-1（schema 瘦身）吃掉，DSL 只在基准证明剩余收益显著时再评估。
  • 多框架渲染器 / A2UI / email 导出。我们是 Electron + React 单平台产品，无互操作需求；这是框架型项目的生存需求，不是我们的。
  • 工具浏览器直连执行。与我们的围栏模型直接冲突（对方文档自己承认鉴权靠应用自觉）。若做画布数据绑定，走 P2-1 的会话 data/ 限定通道。
  • 逐 chunk 全量重解析的流式实现。性能上可行但对 Electron 渲染进程不友好；我们要做也是 partial-JSON 增量解析 + 骨架层保守渲染（P0-2 的形态）。
  • 40+ 组件的全量扩张。对方没有逃生舱所以必须广铺组件；我们有画布兜底，内联组件应按"真实使用频率"补（chart 之后的候选应来自会话数据，不是对方目录）。

7结论

我们的双层架构（6 个高结构化内联组件 + 三层围栏画布）和安全 / 治理纵深是对方给不了的，方向不用改。对方真正领先的是"体验工程"四件套：流式渐进渲染、客户端响应式运行时、紧凑 prompt 工程、增量编辑——其中前三项都能在不动我们安全模型的前提下，通过 genui/impl 已预留的缝隙（目录两层索引、DataTable 客户端钩子、ui-event payloadSrc、activity 解析点）吸收进来。

建议的下一步：实测 render_ui schema 真实 token 数 → 立项 P0-1（客户端视图闭环）+ P0-2（骨架流式）→ 排期 P1-1（schema 瘦身）与 P1-2（重开 ADR 0021 chart 决策）→ 建立自有基准（P2-2）作为后续一切格式实验的前置尺子。另有两处文档口径漂移（system.ts 画布节 "no host bridge" 未随 POO-103 更新；spec-poloai-protocol-bidirectional.md v2 方向描述与实现不符）建议顺手修掉。
