# POL-94 第二轮支付实施编排计划

> 状态：设计与需求已冻结，进入实施编排
>
> 日期：2026-08-23
>
> 适用分支：`POL-94/feat/product-space-credit-recharge`

## 1. 目标与边界

本计划把 [第二轮支付需求基线](./payment-requirements-round2-handoff.md) 和 [用户流程与页面状态](./payment-round2-user-flows-and-page-states.md) 转换为可拆分、可验收的实施批次。

本轮首先实现：

- ProductSpace 余额、按量授权、扣减、释放和追加流水；
- Polo 助手与本地 App 的按实际用量计费；
- 一次用户可理解的 App 任务对应一个 App Run；
- App Catalog/Index 直接启动、首次安装确认和 Polo App Tab 平台状态；
- 积分不足阻断、充值返回后的用户点击查询和手动恢复；
- 支付中心中的不可点击消耗记录。

明确不实现：

- App 操作级固定报价、整 App 一次性固定价格或报价确认/过期/结果中转页；
- Polo 承载 FDE App 的任务输入、执行过程、结果或最终交付 UI；
- 在 FDE App 内强制统一的价格展示组件；
- 自动轮询充值、自动重试被阻断的 App 操作；
- 真实商户、税务、法务和创作者分成参数未确认前的生产收款开放。

固定价格能力保留为未来扩展，排期未定。本轮可以保留服务端内部的 App 版本计量费率快照，但它不是面向用户的固定报价，也不能驱动 Polo 报价页面。

## 2. 现有实现基线

### 2.1 已存在且应复用的能力

`docs/billing-metering-contract.md` 已定义并在当前代码中提供：

- `GET /api/product-spaces/{productSpaceId}/billing`：ProductSpace 余额、支付状态、预算和配额的权威读取；
- `POST /api/billing/runs`：启动 ProductSpace 范围的助手或 App Run；
- `PATCH /api/billing/runs/{runId}`：结束 Run；
- `POST /api/billing/usage`：幂等用量回执、原子授权和账本扣减；
- App 安装、当前发布版本和 Catalog 可见性校验；
- 个人/企业 ProductSpace 付款主体解析、预算/配额阻断和追加补偿事实。

当前 `src/lib/billing/service.ts` 中的 `costMicrosPerToken` 是服务端按量计费费率快照。实施时不得把它解释为用户可见的 App 固定价格。

### 2.2 与 POL-94 冻结规则的差距

| 差距 | 当前基线 | 第二轮要求 | 处理批次 |
| --- | --- | --- | --- |
| App Run 归集 | 服务端可记录同一 Run 的多条内部用量回执 | 用户在消耗记录中只看到一条按 App 名称归集的记录 | A-1 |
| 无可用输出 | 现有按输入/输出 Token 记录用量 | 没有可用输出不扣费；部分输出按实际部分计费 | A-1 |
| Run 异常结束 | 有显式结束接口 | App 崩溃或长期未结束时由 Polo 超时收口 | A-1 |
| App 启动体验 | 服务端已有安装/版本权限边界 | Catalog/Index 直接打开；首次安装确认后自动安装、启动、打开 | B-1 |
| 平台级阻断 | 服务端可拒绝新授权 | 当前 App Tab 非模态提示，按角色提供去充值/通知 Owner | B-2 |
| 充值恢复 | 有余额读取入口 | 用户返回后点击一次查询，不轮询、不自动重试 | C-1 |
| 用户账单展示 | 内部回执和账本事实已存在 | 四位小数、不可点击、只显示时间/能力名称/变动 | C-2 |

## 3. 实施批次与依赖

```text
A-0 规则与接口冻结
 ├─ A-1 App Run / 用量归集与扣费语义
 │   └─ A-2 超时、幂等与异常收口
 ├─ B-1 Catalog / 安装 / 直接启动
 │   └─ B-2 App Tab 平台阻断与角色动作
 └─ C-1 支付中心订单与充值返回查询
     └─ C-2 消耗记录展示与跨端恢复

A-1 + A-2 + B-2 + C-1 + C-2
 └─ D-1 跨端 E2E、对账和灰度门槛
```

依赖规则：

1. A-0 完成前不新增客户端计费文案、接口字段或固定价格占位。
2. A-1/A-2 是 B-2 的服务端权威基础；客户端不能自行推断余额或扣费结果。
3. C-1 必须提供可验证的订单状态查询，C-2 才能实现充值返回后的单次查询。
4. D-1 之前不开放真实微信/支付宝生产配置。
5. 固定价格能力不进入上述依赖图，不得阻塞按量计费交付。

## 4. 批次任务

### A-0：规则与接口冻结

**输出**：一份可供客户端、FDE 和服务端共同使用的 App Metering Contract，作为本计划的补充附件或后续 ADR。

必须冻结：

- `AppRun` 的创建、进行中、完成、失败、取消、未知和超时状态；
- FDE 为一次用户可理解任务创建一个 Run，内部 AI 调用只携带同一 Run ID；
- 内部用量回执可以多条，但用户可见的消耗记录按 Run 聚合为一条；
- Polo 服务端保存 ProductSpace、App、版本、操作者、时间、内部用量和账本事实；不保存 App 输入、文件、Prompt 或输出内容；
- FDE 后处理失败不等于 AI 算力失败；AI 已正常返回后仍按实际算力计费；
- 无可用输出时不扣费，部分输出按可计费实际用量扣费；
- 客户端只能提交 ProductSpace、Run/请求标识和用量事实，不能提交 payer、余额、价格或成功状态；
- 本地 App 不接受 Polo 报价确认或结果回传页面。

### A-1：App Run、用量归集与扣费语义

**服务端**

- 复用 `POST /api/billing/runs`、`POST /api/billing/usage` 和 Run 结束接口；
- 保留版本级内部计量费率快照，禁止客户端选择费率；
- 将同一 Run 的内部用量回执归集到一个用户可见 Usage Record；
- 明确可计费用量判定：无可用输出不形成扣减/消耗记录；部分输出只扣实际部分；
- 保持账本、用量回执、Run 总量和归集记录的不可变/追加事实关系；
- 相同请求幂等重放只返回原事实，改变 Run、空间、操作者、版本或用量指纹必须拒绝。

**验收**

- 一个 App Run 内发生多次 AI 调用，支付中心只出现一条 `App 名称 · 消耗 N.NNNN 积分`；
- 无可用输出不出现 `消耗 0.0000`；
- 部分输出的扣减不超过实际返回的可计费用量；
- 原始内部回执可供对账，但不直接作为用户逐条账单；
- 固定报价、预计剩余和结果页字段不存在于本批次接口和客户端协议。

### A-2：超时、幂等与异常收口

- 为长期处于 `running` 的 App Run 定义服务端超时阈值和收口任务；具体时长作为配置，不写死在客户端；
- 超时只结束未完成 Run，不伪造成功输出、不自动重试、不改写已经形成的账本事实；
- 超时前已有可用输出按实际用量结算，无可用输出则释放授权且不扣费；
- FDE 重复结束、网络重试和 Polo 任务恢复都必须幂等；
- 对未知供应商/未知支付状态继续 fail closed，保留查询和运营核对路径。

### B-1：Catalog、安装与直接启动

**Polo 客户端**

- Catalog/Index 卡片展示“按实际用量计费”，不展示预估价格、固定报价或 Token/模型成本；
- 已安装 App 一次点击直接打开 App Tab；
- 首次安装只确认版本、下载大小和权限，确认后自动下载、安装、启动和打开；
- 未新增权限的更新不重复确认，新增权限时重新确认；
- Polo 只负责启动、安装、权限和本地 API 接入，不规定 FDE App 内任务布局。

**验收**

- 已安装 App 进入任务首页不经过 Polo 报价或结果中转页；
- 首次安装最多两次关键点击；
- App Tab 保留返回 Polo 和切换空间能力；
- 失败状态不会误显示为已安装或已启动。

### B-2：App Tab 平台阻断与角色动作

- localhost API 因积分不足拒绝本次请求且不产生扣费；
- Polo 在当前 App Tab 叠加非模态平台提示，App 内容保持原状；
- 个人用户/Enterprise Owner 显示“去充值”；Manager/Member 显示“通知 Owner”；
- 不关闭 App、不替 FDE 重试、不在 App 内插入 Polo 任务页面；
- 充值到账后只解除平台阻断，用户必须在 FDE App 内重新发起任务。

### C-1：支付中心订单与充值返回查询

**浏览器支付中心**

- 商品、人民币订单、支付渠道、回调和发放属于浏览器/服务端边界；
- 订单目标始终由服务端从 ProductSpace 确定，客户端不能自报付款人或到账状态；
- Polo 客户端打开当前 ProductSpace 的算力商品页，不自动选商品、不自动下单；
- 用户返回客户端后看到“是否已完成充值？”；只有用户点击“已完成，查询结果”才发起一次订单/权益/余额查询；
- 查询处理中、未查到、失败和余额仍不足均可由用户再次点击查询；客户端不轮询。

### C-2：消耗记录与跨端恢复

- “积分 -> 消耗记录”只展示正式扣减和追加返还/补偿事实；
- 每行固定显示时间、`Polo 助手` 或 App 名称、四位小数积分变动；
- 单条不可点击，不展开余额、成员、模型、Token、供应商或内部调用详情；
- 原始消耗记录不可修改或删除，返还/纠错以追加行表达；
- 充值返回保留原 App Tab，不自动重试；用户在 App 内重新发起后创建新 Run。

### D-1：跨端 E2E、对账和灰度门槛

覆盖以下端到端路径：

1. Catalog → 安装确认 → 直接打开 App → App Run → 实际扣减 → 一条消耗记录；
2. App Run 多次内部 AI 调用 → 一条用户记录 → 账本/用量回执可对账；
3. 无可用输出 → 不扣费；部分输出 → 部分扣费；FDE 后处理失败 → 不自动退款；
4. 积分不足 → API 拒绝且不扣费 → 非模态提示 → 浏览器充值 → 用户点击单次查询 → App 保持原状 → 用户重新发起；
5. 个人、Enterprise Owner、Manager、Member 的动作和可见范围分别符合权限矩阵；
6. 重复回调、迟到支付、金额不符、未知状态、Run 超时、重复用量和对账差异均 fail closed。

真实收款开放前，必须满足 [需求基线的生产门槛](./payment-requirements-round2-handoff.md#23-正式开放真实收款的门槛)。

## 5. 待输入与阻塞项

以下事项不阻塞当前按量计费原型，但阻塞对应的生产能力：

| 输入 | 阻塞范围 | 责任方 |
| --- | --- | --- |
| 供应商成本公式、计量单位和用量回执 SLA | A-1 最终计费实现、对账 | 计费/供应商 |
| App Run 超时默认值和 FDE 结束协议 | A-2 生产收口 | Polo + FDE |
| 商品金额、积分数量、退款/发票/税务口径 | C-1 真实收款 | 支付/法务 |
| 真实微信/支付宝商户参数与回调验签 | C-1 生产通道 | 支付运营 |
| 消耗记录聚合查询与分页性能指标 | C-2/D-1 | 计费服务 |
| 固定价格 App 的排期和 FDE 展示规范 | 未来固定价能力 | 产品 + FDE |

在这些输入到位前，不虚构价格、不打开真实支付、不把固定价格写入本轮实施任务。

## 6. 交付顺序与完成定义

推荐顺序：

1. 完成 A-0 合同和字段评审；
2. 完成 A-1/A-2 服务端计量语义、归集、超时和自动化测试；
3. 并行完成 B-1/B-2 Polo 客户端启动与平台阻断；
4. 完成 C-1/C-2 支付中心、单次恢复查询和消耗记录；
5. 完成 D-1 跨端 E2E、对账和灰度验收；
6. 通过生产门槛后，才允许显式配置真实支付渠道。

POL-94 的本轮交付完成定义：

- 所有按量计费路径均不依赖 Polo 报价确认页；
- FDE App 任务 UI 与 Polo 平台 UI 的责任边界在接口和验收中可验证；
- 每个 App Run 的用户可见账单事实可追溯、不可点击、不可改写；
- 积分不足恢复不轮询、不自动重试，角色动作正确；
- 固定价格能力仍保持延期状态，没有被隐式实现。
