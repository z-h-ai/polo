# 四端产品重新对齐：总入口

## Intent（draft；用户已授权组织本轮工作）

用户原意：最近 Polo Client 与 Polo Admin 迭代后，仍感觉功能缺少、流程未梳理清楚；尤其首页 Platform admin login、企业管理端登录、创作者工作台登录令人困惑。四端 policy skill 缺失，用户也不知道还有哪些功能/规则没有讨论。希望通过 ai-native-sdlc 按四端分别在 Notma 访谈，先弄清从哪里开始。

期望结果：用户只从一个任务入口开始，先理解谁从哪里进入、进来做什么、失败怎么恢复；再分别确认四端功能，最终获得跨端一致的 Spec、可发现的政策和可以追溯的增量实施清单。

## 推荐顺序

1. 先做“共享身份、登录与端边界”：复用既有模型，解释并评审三登录入口的真实用户路径。
2. 分端访谈建议顺序：Polo 客户端 → 企业管理端 → 创作者中心 → 平台运营端。各端可先做只读功能盘点；涉及共享身份的 Spec 定稿依赖第一项对应规则明确确认。
3. 四端结论汇合：重放跨端旅程，清理矛盾、确定政策 owner/source，包装共享核心与四端适用规则，建立增量实施清单。

总入口是导航与汇总，不给每个阶段再造一批卡。共享身份卡是第一张实际工作卡；父卡完成不是子卡启动条件。四端盘点不等待已有开发任务全部完成。

## 本次初步发现

三登录入口在 Admin 集成分支可见，POL-88 与已确认四端文档也明确了独立会话和端间无互跳。当前问题至少涉及既有规则是否符合用户体验、首页是否表达正确、所看环境是否包含目标实现；仅修改登录文案无法证明流程闭合。

具体例子：小李同时是企业 Owner 和创作者，旧文档要求从客户端分别进入浏览器管理端，企业/创作者之间退出后重新登录；集成首页却并列公开显示三入口。先核对该首页用途、普通用户应从何进入、深链怎么处理、独立会话与显式退出的关系；不要直接推导为合并身份或新增 SSO。

## 汇总产物与完成标准

- 四端各自的目标用户、功能覆盖、入口和恢复流程可逐条审阅；遗漏由 Agent 盘点提出，而不是让用户凭空补需求。
- 有统一的身份/端边界、跨端交接表与可点击代表旅程；旧确认保留，变化有范围和明确决定。
- 功能缺口逐条指向既有 POL/POO 任务或必要增量，显示“有定义/可执行/已验收”的证据差异。
- policy 矩阵区分已有规则未封装、来源不足、规则冲突、真正缺失；每项有 owner、权威来源、生效范围和后续动作。
- 最终政策/规范的仓库落点和跨仓库消费方式可追溯，不再只依赖单个工作树的相对链接。任务正文记录讨论与确认；进入仓库的可复用政策必须绑定已接受的来源和版本。
- 产品 owner 确认各卡 Spec 后才生成相应实现 Plan；技术负责人确认 Plan 后再按明确执行授权进入交付。已有运行继续使用锁定快照，不将本轮草案注入活跃执行。
