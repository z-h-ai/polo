## 3. 设计契约

### 3.1 四端共享基础

先形成 `docs/four-end-design-foundation.md`，冻结四端共用的：

- Polo 品牌色、语义状态色及可访问性对比度；
- 字体、字号、间距、圆角、阴影、层级和动效；
- 按钮、表单、搜索、筛选、表格、卡片、Badge、Toast、空状态；
- Dialog、Drawer、危险操作确认、重新验证和不可修改审计预览；
- 正常、空、加载、失败、受限和操作结果的统一表达；
- 焦点、键盘、禁用、只读和权限原因的统一规则。

现有 Polo `docs/DESIGN.md` 是 Electron 客户端的直接视觉来源，不作为三个管理端的布局模板。三个管理端复用品牌与基础组件语义，采用成熟的 Web 管理后台信息架构。

### 3.2 产品 HTML 与评审工具严格分离

以下规则为硬性门禁：

- 四端 `index.html` 只呈现真实产品应该呈现的界面、文案和交互。
- `before.html` 与 `after.html` 也只能呈现产品，不显示流程编号、状态选择器、设计说明、来源说明或评审意见。
- 不在产品 HTML 中加入隐藏评审抽屉、悬浮评审条、流程跳转器或测试面板。
- 场景、主题和语言可以通过 AB 原型 URL query protocol 注入，但产品页面内不能显示对应控制器。
- Before/After 切换、流程和状态控制、视口选择、来源追踪与评审说明只能存在于独立的 `comparison.html`、产品入口评审中心、manifest 和 `review-record.md`。
- 评审工具的外观不能被误认为生产产品的一部分。

## 4. Polo 客户端产品结构

### 4.1 工作台外壳

- 使用“工作台外壳 + 多应用 Tab”。
- 顶部工作台栏承载空间切换、应用 Tab、运行状态、通知和账号入口。
- 不设置常驻的全局左侧栏，避免客户端侧栏、助手侧栏和 App 侧栏重复嵌套。
- 首页是固定入口，不作为普通 App Tab 关闭。
- 一个 App 默认只有一个 Tab；再次打开时回到已有 Tab。只有 App 明确支持多实例时才允许新实例。
- App 内部路由继续留在该 App Tab，不把每个页面生成新的客户端 Tab。

### 4.2 空间与启动

- Tab 绑定当前 ProductSpace；“我的空间”和每个企业空间分别保存自己的 Tab 会话。
- 新用户登录后进入“我的空间”首页。
- 老用户进入上次仍然有效的空间，恢复安全的 Tab 和草稿状态，但默认激活首页。
- 不自动恢复或重新启动上次执行；中断任务明确提供继续或终止选择。
- 上次空间失效时回到“我的空间”并解释原因。
- 当前空间仍有活动执行时，必须先完成或终止才能切换空间。

空间菜单只负责在“我的空间”和已加入的企业空间之间切换。创作者圈子不出现在空间菜单中。

### 4.3 首页与内置应用

首页以应用为中心，依次呈现：

- 继续使用和最近打开；
- 当前空间已添加的 Apps；
- 当前空间可用但尚未添加的 Apps；
- Polo 内置应用；
- 当前空间可供 Polo 助手使用的 Skills；
- 最近结果、中断任务和内容变化。

首版内置应用：

- Polo 助手；
- 文件；
- 任务与结果。

设置从账号菜单打开，不占用常驻 Tab；下载进度放在顶部运行状态入口。

### 4.4 Polo 助手与 Skill

Polo 助手是一个内置应用，不是客户端外壳。其核心工作区采用演进式改造：

- 尽量保留真实源码中的会话列表、消息布局、输入框、附件、代码块、文件、工具调用、执行进度、结果和错误反馈；
- 允许调整外围结构、菜单归属、空间标识、Skill 管理入口以及与顶部 Tab 的衔接；
- 账号、空间切换、应用目录、下载中心、全局文件、通用偏好和管理端入口移出助手。

Skill 是 Polo 助手的扩展能力：

- 不能独立打开，不生成 Tab；
- 由用户在 Polo 助手中启用、停用和选择；
- 调用过程、权限确认和结果都显示在助手对话中；
- 首页或 App 详情可以说明当前空间可用的 Skills，但不把 Skill 伪装成 App。

### 4.5 App、运行、权限、文件与结果

- 授权后的 App 先进入“可用应用”，用户可以“添加到首页”；不模拟传统软件下载，除非确实有本地资源包。
- App 主体在 Tab 中运行，顶部保留薄型 Polo 可信栏，显示 App 名称和来源、当前空间、版本、连接/运行状态、权限入口和更多操作。
- App 不能伪造空间身份、Polo 权限确认或费用提示。
- 同一空间内切换 Tab 不终止运行。
- 关闭正在运行的 Tab 时，让用户选择继续后台运行或终止；后台运行进入顶部运行中心和“任务与结果”。
- “任务与结果”只展示 Polo 掌握的运行状态、最小计量和明确保存的结果，不创造统一 App 业务工作项协议。
- “文件”按当前空间展示用户上传、App 保存、助手生成和用户导出的文件，并标记来源、创建者、空间和时间。
- App 只能读取用户明确选择的文件或已授权目录。

权限采用三层确认：首次启用统一说明；权限扩大时重新确认；高风险动作每次确认。Skill 的确认在助手对话中完成，App 的确认由 App Tab 内的 Polo 可信外壳承载。

### 4.6 账号、通知和管理入口

- 账号菜单包含全局设置、企业组织管理端和创作者工作台入口。
- 企业组织管理端和创作者工作台在系统浏览器中打开，不作为客户端 App Tab。
- 平台运营端不出现在普通客户端。
- 通知中心可以跨空间聚合，但每条通知必须明确标记空间；点击其他空间通知时遵守空间切换和活动执行阻塞规则。
- 全局设置只管理账号与安全、外观和语言、通知、本机存储和下载、网络和更新、高级运行配置以及 App/Skill 授权记录。
- 企业成员、预算、目录、作品和圈子等业务配置必须进入对应管理端。

### 4.7 主题与视口

- Polo 客户端正式实现浅色和深色。
- 桌面窗口是产品目标；同时验证常见小窗口宽度。
- AB 抓图仍声明窄视口，用于检查最小窗口保护或窄窗口降级，不把它解释为移动端产品承诺。

## 5. 三个管理端产品结构

### 5.1 公共壳层

三个管理端共享同一套 Admin 设计系统和基础壳层：左侧一级导航、顶部上下文与账号区域、主内容区、详情 Drawer、Dialog、表格和反馈组件。它们不通过更换品牌主色伪装成不同产品。

共同权限规则：

- 完全无权进入的产品或模块隐藏入口；
- 已进入模块但角色不能执行的操作保留并禁用，同时解释原因；
- 因欠费、治理、资格或临时状态受限时保留数据并只读展示原因、恢复条件和责任人；
- 当前版本不存在的能力不显示。

管理端以 1440px 桌面为主要视觉目标，并保证 1024px 平板横屏可操作。手机端只覆盖登录、状态查看、紧急确认以及明确的桌面端提示，不为手机重排全部复杂管理流程。

### 5.2 企业组织管理端

- 只允许目标企业的 Owner/Manager 进入；Member 不显示入口。
- 顶部提供企业切换器，支持同一账号管理多个企业。
- 首页采用“企业状态 + 待办行动 + 最近变化”，重点呈现成员、目录、预算、限制和 Owner/Manager 需要处理的事项。
- Manager 可看到 Owner-only 操作及其禁用原因，但不能触发对应 Dialog 或写操作。

### 5.3 创作者工作台

- 只允许具有有效创作者资格的普通账号进入。
- 圈子不是 ProductSpace，也不作为全局工作台切换器；页面使用圈子筛选器。
- 作品属于创作者账号，圈子只是分发渠道。
- 首页采用“资格状态 + 待办行动 + 最近变化”，重点呈现作品发布进度、圈子经营、收入、质量和待处理反馈。
- 资格暂停或撤销时保留责任处理、导出和申诉所需的只读入口。

### 5.4 平台运营端

- 使用独立工作人员账号登录，不与普通账号或前两个管理端混用。
- 不设置企业或圈子切换器，通过全局搜索、稳定 ID 和行动队列定位对象。
- 首页采用“平台健康 + 行动队列 + 最近治理变化”，优先展示需要领取和处置的事件。
- 高风险动作必须重新验证、填写原因、核对影响，并产生不可修改审计记录。

## 6. AB 原型交付结构

每条用户流程使用 `AB-prototype` 形成独立评审包，四个产品入口再分别提供整端产品 HTML 和独立评审中心。

```text
design-demos/<product-slug>/
├── index.html                     # 只呈现完整产品，不含评审 UI
├── assets/                        # 整端产品共享资源
├── screenshots/                   # 整端产品截图
├── prototype-manifest.json        # 整端来源和覆盖摘要
├── review-record.md               # 独立评审与冻结记录
├── reviews/
│   └── index.html                 # 四端之一的独立评审中心
└── flows/
    └── <flow-id>/
        ├── before.html            # 产品界面，不含评审 UI
        ├── after.html             # 产品界面，不含评审 UI
        ├── comparison.html        # 独立 Before/After 评审工具
        ├── prototype-manifest.json
        ├── assets/
        └── screenshots/
```

每个流程包必须：

- 从当前源码刷新 Before；
- 为相同语义场景提供 Before 与 After；
- 使用统一的 `scene`、可选 `theme` 和可选 `lang` query protocol；
- 将样式和资源标为 `exact`、`derived` 或 `approximate`；
- 对缺乏源码证据的值使用最小范围近似并记录原因；
- 使用真实断点，至少声明桌面和窄视口；
- 截图覆盖 Before、After、所有场景和声明视口；
- 通过 AB bundle validator 和真实浏览器检查。

语言矩阵从真实产品能力推导：源码支持多语言的流程必须声明并验证对应语言；不支持时不制造假的语言切换器。产品入口默认使用中文评审数据和正式中文文案。

## 9. 验收矩阵

### 9.1 每条流程

- 有独立 Before、After、comparison、manifest、assets 和 screenshots。
- 正常、空、加载、失败、受限及关键操作结果按流程实际需要完整覆盖。
- 所有状态均可通过确定性的 query 或真实产品交互复现。
- Before/After 使用相同场景语义，不出现参数漂移。
- 资源使用本地相对路径；仅允许 AB 契约指定的固定运行时 CDN。
- 无未声明近似项、模板占位符、控制台错误和资源失败。

### 9.2 每个产品入口

- `index.html` 不包含评审工具、流程编号、状态切换器、设计说明或来源说明。
- 正常产品导航可以到达关键流程，评审中心不能代替真实交互。
- 权限差异、危险操作、恢复路径和责任边界符合产品文档。
- 产品文案真实、稳定标识一致，不使用 lorem ipsum 或无意义占位数据。
- Polo 客户端浅色和深色通过；三个管理端浅色通过。
- 桌面、平板/窄窗口和声明的手机降级状态通过。
- 键盘、焦点、弹窗关闭、禁用状态和错误反馈可用。

### 9.3 G4-B 完成定义

G4-B 只有同时满足以下条件才通过：

- 46 条流程全部拥有独立且通过校验的 AB 评审包；
- 四个产品入口的整端 HTML 全部通过真实浏览器交互验收；
- 产品 HTML 与评审 UI 完全分离；
- Before 来源、样式、资源和近似项可追溯；
- 四个 `review-record.md` 写入确认日期、确认人和 commit；
- 冻结结果回写所有相关实施任务；
- 产品用户明确确认四端冻结。

## 10. 并行与依赖

- Phase 0—Phase 1 先完成共同事实和设计契约，避免四端各自发明规则。
- Polo 客户端壳层与 Admin 公共壳层可以并行。
- 公共壳层确认后，四条黄金流程可以并行。
- 黄金流程冻结后，四端剩余流程可以按入口并行展开。
- 每端可以独立通过壳层、黄金流程和整端冻结，但 G4-B 必须等待四端全部通过。
- G4-A 与 G4-B 同时通过前，不启动 POL-72 或后续正式产品编码。

## 11. 人工暂停条件

执行过程中只在以下情况请求产品裁决，并附具体用户场景、可观察影响和推荐方案：

- 真实源码与已确认产品流程存在无法同时满足的冲突；
- 必须改变四端一级结构、空间/Tab/账号关系或产品入口；
- 必须改变角色、权限、付款、数据归属、治理责任或高风险确认；
- 某条流程缺少足以判断产品语义的文档；
- 技术约束导致产品 HTML 无法与评审工具彻底分离；
- 覆盖目标超出现有四个明确的设计产物目录。

样式提取、组件拆分、fixture、截图脚本、校验脚本和已确认范围内的缺陷修复不需要再次请求裁决。
