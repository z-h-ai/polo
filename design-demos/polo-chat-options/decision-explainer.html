01QuestionRequest 组件长什么样（可以直接点）

Agent 遇到"会改变结果的选择"时调用 request_user_input，普通输入框被这个组件接管。这是一个真实可交互的复刻：单选题 → 点下一步 → 多选题 → 其他/组合 → 确认或暂不回答。

把项目删除流程补完整。
删除方式会影响数据能否恢复，我需要先确认一个选择。
  • 1每题 2–4 个预设选项，单选（圆点）或多选（方块）。题头右侧徽章显示「当前题 / 总题数」，最多 3 个连续问题。
  • 2推荐项带紫色徽章和一句话理由（"可在 30 天内恢复"），由 Agent 给出，不是 UI 猜的。
  • 3"其他"由 UI 自动补充，Agent 不用自己生成；选中后展开文本框并聚焦。多选题里"其他"可与普通选项同时勾选；只有协议显式标记为排他的选项（如"不发送通知"）才会清空其他选择。
  • 4必答未完成时下一步/确认禁用；提交中全部控件禁用防重复；瞬时失败在组件内提示并保留选择可重试。
  • 5"暂不回答"始终在底部：清除待回答状态、Agent 不会在没有答案的情况下继续，恢复原草稿和普通输入框。请求不因时间过期，只有被回答 / 暂不回答 / 新请求取代 / 会话停止归档删除才失效。
  • 6确认后，回答以可读用户消息进入会话历史，Agent 在原会话上下文恢复执行。

💡 试试：单选题选"永久删除" → 下一步 → 多选题同时勾"项目管理员" + "其他"并输入文字 → 确认，底部会展示真实提交给 Agent 的结构化 payload；再试试"暂不回答"看取消终态。

02冲突在哪：四种回合，Edit Popover 卡在中间

"仅桌面交互入口注册"落到实现上，是按 session 的可见性与形态判定资格。hidden + mini 这个形态同时被两种入口使用——这就是冲突的技术根源。

关键区别：Edit Popover 与消息渠道的 session 形态相同（hidden + mini），但交互性质相反——前者有真人坐在屏幕前，后者没有。形态规则区分不了它们，所以需要一个"来源可信"的显式信号。

📌 代码事实（EditPopover.tsx）：创建会话时 hidden: true（:972）+ systemPromptPreset: 'mini'（:969）——这就是"hidden + mini"的出处；而浮层内已取 usePendingQuestion(inlineSessionId)（:778）并把 pendingQuestion 传给 ChatDisplay（:1069-1070）——结构化问题组件在 Edit Popover 里的挂载点已经接好，缺的只是会话资格位允许工具注册。这也是方案 A 改动极小的原因。

03+小浮层里装得下吗？—— QuestionRequest 的适配机制

Edit Popover 默认 400×480、最小 300×250。QuestionRequest 没有 compact 专属变体，靠的是流式布局 + 高度钳制，本身就为小容器设计：

  • 1高度自适应：隐藏测量 div + ResizeObserver 实测内容高（InputContainer.tsx:160），question 回退 320px；钳制 = min(480px 硬顶, 主窗口高 × 70%)、下限 160px（structured-height.ts）。超限时内容区内部滚动 min-h-0 flex-1 overflow-y-auto（QuestionRequest.tsx:238），footer shrink-0 固定（:312）——操作按钮永远可达。
  • 2窄宽防溢出：选项文字 min-w-0 flex-1（:209）、圆点/方块标记 shrink-0（:201）、题头 min-w-0（:240）——300px 最小浮层宽下长文案换行不溢出；步数徽章仅多题时才渲染（:249），单题不占宽。
  • 3compact 通道已有：InputContainer 接 compactMode（freeform 回退 70px 紧凑档）；QuestionRequest 布局全流式，不依赖固定尺寸。
  • 4验证：QuestionRequest.test.tsx 15 pass / 0 fail（选择 / Other / 排他 / 多题导航 / 取消 / 瞬时失败重试 / 键盘 / a11y），另有 input-container-question-promise.test.tsx 覆盖提交/取消链路。
