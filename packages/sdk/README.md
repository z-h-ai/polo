# @polo-ai/sdk

Browser-only single-query AI for authorized local Polo Apps. The creator writes a frontend; Polo owns the backend, provider credentials, account/space authorization and billing. End users do not install Node or start a backend. The SDK does not expose provider keys, identity selection, arbitrary RPC, filesystems, tools or CLI execution.

```ts
import { polo, PoloError } from '@polo-ai/sdk'

const available = await polo.isAvailable()
const result = await polo.prompt({
  prompt: '根据已确认的需求提出项目建议，只返回 JSON',
  responseFormat: 'json_object',
})
// Validate result.text as application data before using it.

const task = polo.run({ prompt: '整理选定需求', responseFormat: 'text' })
const unsubscribe = task.onStatus(({ phase }) => console.log(phase))
cancelButton.onclick = () => { void task.cancel() }
try { const result = await task.result } finally { unsubscribe() }
```

`run` is the same **single query** as `prompt`. It adds lifecycle observation and cancellation. It is not an Agent tool loop or token streaming. Status events reflect Main boundaries: `starting`, `running`, `settling`, then `completed`, `cancelled` or `failed`. `settling` begins after query returns; query internally includes usage receipt work. Final text is released through the existing Host validation/usage boundary, never sliced into pretend tokens.

## Input and output

Only `prompt`, optional `systemPrompt`, `responseFormat: 'text' | 'json_object'`, `maxOutputTokens` (default 4096, 1–8192), `timeoutMs` (default 60000, 1000–120000), and browser `signal: AbortSignal` are accepted. Prompt must be nonblank and at most 1 MiB UTF-8; system prompt at most 512 KiB. Main repeats authoritative validation. Unknown fields (including apiKey, provider, baseUrl, account, workspace, appId or payer) are rejected.

Result: `{ status: 'completed' | 'partial', text, requestId, settlement }`. `requestId` is a content-free UUID generated by Main. Application JSON still needs domain validation; `json_object` is not a guarantee that a quote is valid. `partial` means an incomplete query outcome; it remains partial in the SDK and the example blocks confirmation/export. Billing finish maps both completed and partial query outcomes to the existing `completed` run status, because Admin has no partial enum.

`settlement` is independent of query completion: `confirmed`, `no_charge`, `pending`, or `unknown`. For pending, say “建议已生成，计量待确认”; unknown is not success. The SDK never resends a prompt. A cancellation acknowledgement does not prove that no provider work occurred. The task settles after original-run bounded cleanup; a late cancel preserves a completed provider outcome. Closing, reloading, navigating, stopping the runtime, switching scope/account or losing authorization invalidates old calls. No old text is delivered to a new document.

Receipt/admission recovery reuses Polo's original-identity outbox. Finish is **not** durably stored in that outbox: Main attempts bounded per-run cleanup with an independent signal. Unconfirmed finish remains unknown for subsequent existing teardown/server timeout handling. There is no promise of persistent finish recovery after process loss.

`PoloError.code` is stable and content-free. Local errors: `host_unavailable`, `unsupported_host`, `invalid_request`. Runtime errors include `capability_invalid`, `insufficient_credit`, `request_cancelled`, `request_in_progress`, `idempotency_conflict`, `run_state_conflict`, `run_finalized`, `host_auth_failed`, `host_configuration_unavailable`, `host_failed`, `host_timed_out`, `no_output`, `metering_unconfirmed`, `shutting_down`, `response_cache_full`, `run_registry_full`, and the existing API validation/route codes. Messages do not expose secrets or internal stacks. A plain browser fails explicitly with `host_unavailable`; there is no public-provider fallback.

## Compatibility and security

SDK version **0.1.0**, bridge protocol **1**. Requires a Polo build containing this bridge; existing released **0.16.3 is not asserted compatible**. Supported: authorized static Apps loaded through Catalog → installation → START → WebAppView. Trusted local UI for process Apps can use the same bridge. Remote URL Apps, ordinary webpages, Browser pane, iframes and standalone dev servers are not SDK hosts. One active query and at most 256 call IDs per document; reload starts a new document without replaying prompts.

The package has no runtime dependencies or Node/Electron types. Import it into a browser build. Host preload/Main enforce real sender/main-frame, one-use isolated preload attach ticket, owning host window/Workspace, exact local origin, document generation, live runtime/scope generation and capability TTL/revocation. Tokens and provider keys never enter the App page. Existing HTTP gateway Origin/CORS policy remains unchanged.

## Quotation example and creator Skill

[Example source](examples/quotation-assistant/) implements prepare → preview → generate/cancel → validate → edit → confirm → CSV/JSON download. The [creator Skill](skills/polo-web-app/SKILL.md) is included in the tarball; it is not installed globally. Text/CSV inputs are user-selected, limited to 256 KiB, strictly decoded as UTF-8 and parsed before use. Prices are integer cents from user-confirmed inputs; totals are recomputed. CSV output escapes formulas; JSON preserves text. No model HTML is inserted. Browser downloads do not give the App arbitrary filesystem access. This sample keeps data in page memory only.

From a project outside this repository:

```sh
npm install /path/to/polo-ai-sdk-0.1.0.tgz
cp -R node_modules/@polo-ai/sdk/examples/quotation-assistant ./quote-app
cd quote-app
npm install /path/to/polo-ai-sdk-0.1.0.tgz
npm run build
npm run package
```

Node 20+ (or compatible Bun), npm and declared esbuild/fflate dev dependencies are creator build requirements. The output `polo-payload.zip` is the Creator upload payload, with `index.html`, `app.js`, `app.css` and `polo-app.json` at its root. No App ID or version reservation is needed. Normal Creator upload assigns the identity/version and writes the final `polo-app.json` with a static file entry and healthcheck `/`; validation, review, publication and distribution establish the authorized Catalog bundle. Keep the upload payload and final bundle checksums distinct. A historical final bundle whose manifest entry is the directory `web` cannot be reused as this upload payload without adapting its entry layout.

The ZIP alone cannot install the App in Polo or grant authorization. Do not publish or grant access without authorization. Real use needs the authorized Catalog/version/download and valid space/provider/billing services. The same generated ZIP includes Enterprise v1 metadata in the single `metadata` object in `scripts/build.mjs`. When deriving the example, update the name, description, icon, instructions, author and source there. Each build generates a fresh local UUID; no platform registration is needed. For a new Enterprise internal import, build and package normally. To update the same local package intentionally, set `POLO_APP_ID` to its previously generated UUID and `POLO_APP_VERSION` to the new version before building. The Owner uses normal import, inspection, version adoption, scope and enablement; the local identity grants no access and does not inherit creator-circle authorization. Creator repackaging replaces this local manifest and may discard its enterprise declarations, so the downloaded Creator final bundle is not interchangeable with the generated Enterprise import ZIP.

Maintainers: `bun run --cwd packages/sdk build`, `bun run --cwd packages/sdk test`, then `npm pack --workspace packages/sdk --pack-destination <delivery-dir>`. Build artifacts and tarballs are generated; maintain this Skill/example source only. A controlled Admin/Provider test proves that transport/runtime path only; it is not real-business E2E or formal product acceptance.
